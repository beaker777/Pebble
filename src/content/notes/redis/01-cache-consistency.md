## 三大缓存故障对比与解法

| 问题类型 | 核心成因 | 典型治理方案 |
| :--- | :--- | :--- |
| **缓存穿透** | 查询**根本不存在**的 Key（如恶意负 ID），请求直穿数据库 | 参数校验 + 缓存空对象（短 TTL）+ **布隆过滤器**拦截 |
| **缓存击穿** | 某个**超高并发热点 Key** 突然过期，瞬间大量请求同时回源 | 分布式互斥锁（仅放行一个线程重建）或**逻辑过期异步刷新** |
| **缓存雪崩** | **大量 Key 同时失效**或 Redis 集群整体宕机 | TTL 加随机抖动 + Redis Cluster 高可用 + 本地二级缓存 + 限流降级 |

## 数据库与缓存双写一致性

工程上最常用 **Cache-Aside（旁路缓存）**：**先更新数据库，再删除缓存**。

```text
写请求：Update MySQL  ──▶  Delete Redis Key  ──▶  （失败则发 MQ / 监听 Binlog 补偿删除）
读请求：Read Redis    ──▶  Miss 时查 MySQL 并回填 Redis
```

> **为什么是「删除缓存」而不是「更新缓存」？**
> 1. **懒加载**：缓存往往涉及多表聚合，写多读少场景反复回写纯属浪费；
> 2. **防并发覆盖**：两个写线程交错更新极易把旧值写回缓存；而「先更库后删缓存」仅在极极端时序下才可能产生脏数据。
>
> 若对最终一致性要求更高，推荐接入 **Canal 订阅 MySQL Binlog**，由独立消费者异步删除缓存并支持失败重试。
