MySQL 并不直接提供乐观锁机制, 而是由我们在应用层基于 **CAS** 的思想实现:

- Select 时, 将业务数据和 `version` 一起读取出来.

- Update 时, 我们将 `version` + 1, 同时在 Where 条件中携带 `version`.

- 通过判断 Update 影响的行数是否为 1 来确定更新是否成功. 为 0 说明执行业务期间数据被修改过, 需要重试或回滚.

虽然乐观锁在执行 Update 的时候仍然加了行锁, 当时我们仍然将其称为乐观锁, 主要是因为:

- 持有锁的时间较短, 悲观锁会在整个业务期间持有锁, 严重影响并发性能.

- 乐观锁在读取和处理业务期间是完全 **无锁** 的, 只在 Update 的时候需要加锁.

因此乐观锁非常适合 **读多写少** 的场景, 如果写操作非常多, 乐观锁会产生大量重试, 这种情况下我会选择使用悲观锁.
