## 为什么选择 B+ 树？

| 结构 | 磁盘 IO 次数 | 范围查询表现 | 为什么不是首选 |
| :--- | :--- | :--- | :--- |
| **红黑树** | 极高（树高动辄 20+ 层） | 较差 | 每个节点只存一个键，退化为大量随机磁盘寻道 |
| **Hash 索引** | 极低（等值 O(1)） | **不支持** | 无法支持 `BETWEEN`、`>`、`ORDER BY` 和最左前缀 |
| **B 树** | 较高 | 中等（需中序回溯） | 非叶子节点也存整行数据，单页扇出大幅缩水导致树变高 |
| **B+ 树** | **极低（3 层存千万行）** | **极佳（叶子双向链表）** | 非叶子节点纯存索引键与指针，单页 16KB 扇出高达 ~1200 |

## 聚簇索引与二级索引（回表）

- **聚簇索引（主键索引）**：叶子节点直接挂载完整的行记录，一张表有且仅有一棵聚簇索引树。
- **二级索引（辅助索引）**：叶子节点仅存放「索引列 + 主键 ID」。若查询列未被该索引覆盖，需拿主键 ID 再查一次聚簇索引，这就是**回表**。

```sql
-- 建立联合索引 (user_id, status, created_at)
-- 覆盖索引：所需列全部在二级索引叶子节点中，Extra 显示 Using index，零回表
SELECT user_id, status, created_at
FROM orders
WHERE user_id = 10086 AND status = 'PAID';
```

## 两大高频优化抓手

1. **最左前缀原则**：联合索引 `(a, b, c)` 按从左到右有序排列，遇到范围查询（`>`、`<`）后右侧列通常无法继续利用索引排序。
2. **索引下推（ICP）**：MySQL 5.6+ 在存储引擎遍历二级索引时，直接先过滤 `WHERE` 中包含在索引里的其他条件，把不符合条件的记录直接裁掉，大幅减少回表次数。
